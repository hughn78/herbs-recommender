## 2. Application architecture

- **Stack:** TanStack Start (React 19 + file-based routing + `createServerFn`
  RPC), Vite 8, Tailwind CSS v4, shadcn/ui (Radix), Supabase (Lovable Cloud),
  Vitest. Nitro/Cloudflare-worker output.
- **Origin:** generated by Lovable from a single "PharmaPrompt OS" prompt
  (README.md is that prompt verbatim — 691 lines, itself the real spec).
- **Server functions** (`src/lib/*.functions.ts`) run engine + DB access;
  there are **no Supabase Edge Functions** despite the README describing them.
- **Two Supabase access paths:**
  - `publicSupabase` middleware (`src/lib/public-supabase-middleware.ts`):
    anonymous, publishable key, `userId` hardcoded `null`. Used by the entire
    clinical flow (cases, engine, feedback, queue, export, product list).
  - `requireSupabaseAuth` middleware: verifies Bearer JWT via
    `auth.getClaims`, used only by ingestion + KB search functions.
  - `supabaseAdmin` (service role, bypasses RLS): dynamically imported inside
    ingestion handlers only. Service key stays server-side. ✔
- **Auth UI:** `/auth` email+password sign-in/up. The `_admin` layout route
  gates `/app/products`, `/app/references`, `/app/rules`, `/app/setup` behind
  a signed-in session (`ssr: false`, client-side redirect to `/auth`).
  The clinical flow (`/app`, `/app/review`, `/app/cases`, `/app/queue`,
  `/app/case/:id`) is **fully public — no sign-in required**.

## 4. Recommendation workflow (as implemented)

`createCaseFn` (`src/lib/cases.functions.ts`):

1. Reads all `safety_rules` + all `reviewed=true` products (anon client).
2. Runs `runEngine` (`src/lib/engine.ts`) — deterministic, no AI, no vectors:
   - `detectPatientFactors` (regex over history/symptoms/pathology + med classes)
   - safety-rules pass (DB-driven, 13 seeded rules)
   - hard-coded `SYMPTOM_MAP` counselling prompts (cramp/fatigue/reflux only)
   - `screenRedFlags` (`red-flags.ts`, 368 lines of curated rules)
   - `checkOtcInteractions` (`otc-interactions.ts`, 613 lines of curated rows)
   - `recommendProducts` (see §5)
3. `attachEvidence` (`retrieval.ts`) — full-text search over `kb_chunks`,
   top 3 per rec, appended to `source_references`. Best-effort; failures
   swallowed. Tier labels 1–5 in words. ✔ honest.
4. `runAiSenseCheck` (`ai-sense-check.ts`) — Lovable AI Gateway,
   `google/gemini-2.5-flash`. **Code-enforced safer-only:** only
   `lower_confidence` / `add_caution` / `flag_for_review` / `no_change`;
   upgrades rejected; confidence on safety_caution can never be lowered;
   candidates capped at 20 by severity; fail-closed on parse error.
   Skips gracefully when `LOVABLE_API_KEY` unset. Audit rows recorded in
   `sense_check_audits` (applied + rejected changes). ✔ Matches mission
   Stage 6 constraints in spirit.
5. Persists case + recommendations + audit with **`user_id: null` hardcoded**.

## 5. Product matching (`recommend-products.ts`)

- Products have `clinical_use_tags` / `avoid_if_tags` (seeded, 103 HOG products).
- Three **hard-coded TS maps**: `DEFAULT_DRUG_CLASS_MAP` (8 classes),
  `DEFAULT_FACTOR_MAP` (16 factors), `DEFAULT_SYMPTOM_MAP` (~25 keywords),
  plus `AVOID_TAG_FACTOR_MAP` / `AVOID_TAG_DRUG_CLASS_MAP` suppression tables.
- Suppression: avoid-tag↔factor, avoid-tag↔drug-class, ingredient vs
  rule `avoid_product_keywords`, ingredient duplication vs existing
  supplements (substring match on a raw free-text blob).
- Deterministic age gate (`isAgeAppropriate`): paediatric-name regex;
  fail-closed suppression of children's products when age unknown. Well
  documented and tested. ✔
- Precision floor: ≥2 matched tags OR ≥1 symptom-derived tag. ✔
- Scoring: flat `400 + 20×matchedTags`; confidence High/Medium by tag count.
  **Score components are not stored** — only the final number.
- `confidence_score: 50` hardcoded on every product rec; engine later flattens
  every product rec to `confidence: "Medium", score: 250` — i.e. **product
  ranking differentiation computed in `recommendProducts` is discarded** by
  the `GeneratedRec` conversion in `engine.ts` (bug/design flaw).
- Every product rec gets 4 byte-identical `pharmacist_checks` and a
  single canned source reference (`tier_label: "Pharmacist-reviewed
  catalogue", note: product_id`) — no per-product citations, no excerpts.
- `source_references` from `attachEvidence` may add real `kb_chunks` hits —
  but `kb_chunks` content is generic pharma KB (TG/AMH/CMI/PI), not HOG
  product documentation.

## 6. Medication parser (`parser.ts`)

- Deterministic: split on `[,;\n\r]` → normalise (strips strengths, dose forms,
  frequency words) → exact generic/brand/alias → prefix match → Levenshtein
  fuzzy on first token (threshold `max(2, len/5)`), fuzzy requires user
  confirmation in the wizard. ✔ never silently accepted.
- Dictionary is DB-seeded (~166 rows, AU brands) — data, not code. ✔
- **Weaknesses vs mission:** strength/dose/frequency/formulation are stripped
  and **discarded**, not retained; no certainty field; brand retained only on
  the chip, not preserved with strength; unknown entries silently ignored by
  the engine (only flagged in UI).

## 8. Authentication & role behaviour

- Roles: `user_roles` table with `app_role` enum; `has_role` SECURITY DEFINER
  function is no longer API-callable (fixed in latest commits).
- Admin check (`assertAdmin` in `ingest.functions.ts`) queries `user_roles`
  via the caller's own RLS-scoped client — server-side, unspoofable. ✔
- **Side effect:** `searchKbFn` (References search) also requires admin →
  ordinary pharmacy staff cannot search references at all. Mission Phase 11
  explicitly wants staff search without admin powers.
- Clinical flow needs no login; every case/rec/feedback row is written with
  `user_id = NULL` and is readable by **any anonymous visitor** (RLS policies
  `USING (user_id IS NULL)` + anon grants). `listCasesFn`, `getCaseFn`,
  `exportCaseFn`, `listQueueFn` all serve anonymous traffic.
- No organisation scoping, no rate limiting, no retention/deletion behaviour,
  no transient ("do not save") mode. Logs: `error-capture.ts` posts errors to
  Lovable's reporting endpoint (worth reviewing payload content).

## 12. Security & privacy concerns (as-found; **unchanged**)

1. **Anonymous public access to all patient cases** — cases carry health
   information (age, sex, pregnancy status, medications, symptoms) and are
   world-readable with only the publishable key. `patient_cases`,
   `recommendations`, `pharmacist_feedback`, `sense_check_audits` all have
   anon CRUD policies on `user_id IS NULL` rows.
2. **No authentication on the clinical flow at all** — contradicts mission
   Phase 13 ("patient reviews require an authenticated staff session").
3. `.env` tracked in git.
4. Case list shows symptoms + labels on a public dashboard (`/app`,
   `/app/cases`, `/app/queue`).
5. `exportCaseFn` (full JSON+CSV export incl. all case fields) callable
   anonymously — no authorisation.
6. KB search restricted to admin — overcorrection; ordinary staff locked out.
7. No rate limiting / abuse protection on any public serverFn.
8. AppleDouble pollution shows the repo is rsynced/FAT-copied around;
   `package-lock.json` untracked while `bun.lock` is stale — dependency
   provenance ambiguous.
9. Raw AI responses (`raw_response`) stored in `sense_check_audits` —
   contains patient summary echoes; acceptable but should be noted in the
   privacy model.
